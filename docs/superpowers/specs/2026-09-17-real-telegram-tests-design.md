# Реальные Telegram-тесты и перевод e2e на Python

Дата: 2026-09-17 · Issue: [#53](https://github.com/42-Z/Mimic42/issues/53) · Статус: черновик

## Цель

Тесты, которые проверяют Mimic в настоящем Telegram: тестовый Telegram-аккаунт
(проверяющий) пишет мимику, мимик отвечает через настоящий Telethon, ответ
приходит проверяющему и фиксируется в базе. Покрытие — рантайм агента, API и
дашборд. Онбординг мимиков — разовая ручная операция вне тестов.

Попутно устраняется источник «мусорных» файловых сессий: бэкенд перестаёт
создавать `.session`-файлы и вместо тихого fallback падает с понятной ошибкой.

## Участники и хранение

Три реальных Telegram-аккаунта, роли не смешиваются:

| Роль | Статус | Данные |
|---|---|---|
| Проверяющий | есть, авторизован | session string генерируется скриптом входа; хранится в тестовом конфиге |
| Мимик 1, Мимик 2 | покупаются | никаких данных в конфиге; сессии создаются штатным онбордом и живут в Dev-базе |

Тестовый конфиг (`.env.test` локально + секреты CI), больше ничего телеграфного:

```
TEST_ACCOUNT_EMAIL=...          # выделенный аккаунт сайта Mimic, владелец мимиков
TEST_ACCOUNT_PASSWORD=...
TG_CHECKER_API_ID=...
TG_CHECKER_API_HASH=...
TG_CHECKER_SESSION=...
```

Ключевые решения:

- **Аккаунт сайта** (`TEST_ACCOUNT_*`) — отдельный от слотовых персон,
  регистрируется в Dev-проекте Supabase один раз
  (`scripts/test_env_bootstrap.py`, если заданы креды). Не входит в `SLOTS`,
  поэтому `purge_slot_data` его не трогает, и сессии мимиков не протухают
  между прогонами. Id нигде не фиксируется: тесты берут owner_id из claim
  `sub` своего JWT — тем же путём, что и прод (`api/auth.py`).
- **Номера мимиков нигде не хранятся**: тесты читают их из Dev-базы
  (`telegram_sessions.phone_number` агентов, принадлежащих `TEST_ACCOUNT_EMAIL`).
- **Проверяющий** — единый Python-хелпер `src/mimic42/testing/real_tg/`:
  Telethon-клиент на проверочной сессии. Асинхронное ядро + синхронная обёртка
  для pytest-playwright (синхронные тесты). Функции: отправить сообщение,
  дождаться ответа с таймаутом; при первом контакте импортирует контакт по
  номеру (приватность свежих покупных аккаунтов).
- **Скрипт первичного входа** `uv run python -m mimic42.testing.real_tg.login`:
  креды берёт из `.env`/`.env.test`, интерактивно запрашивает номер, код (из
  SMS), 2FA-пароль; session string сохраняет в `TG_CHECKER_SESSION` в
  `.env.test`, не печатая его. Используется один раз для проверяющего.

## Перевод e2e на Python

- Зависимость: `pytest-playwright` в dev-группу (uv). Клиент — chromium.
- Тесты в `tests/e2e/`, маркер `e2e`; по умолчанию исключён. Запуск:
  `uv run pytest -m e2e`. Маркер `real_tg` тоже исключён по умолчанию
  (addopts меняется на `not db and not e2e and not real_tg`). Важно: `-m` в
  CLI перекрывает addopts, поэтому каждая CI-джоба пишет маркер полностью —
  иначе юнит-джоба подхватит e2e-тесты и начнёт поднимать серверы.
- Серверы вместо `webServer` из TS-конфига — session-фикстуры в
  `tests/e2e/conftest.py`: поднимают тестовый сервер
  (`uvicorn mimic42.testing.server:app`) и фронт (`next dev`, порты из тех же
  `E2E_API_PORT`/`E2E_APP_PORT`), ждут готовности, глушат после прогона.
- Авторизация: фикстура логинит каждую персону через UI один раз и сохраняет
  storage state в файл; живой и непросроченный файл переиспользуется.
- Скриптовые заглушки остаются HTTP-эндпоинтами `/__test__/*` (для клиента
  без разницы, на чём он написан) — в Python вызываются через httpx.
- Прямые манипуляции с базой — на имеющемся стеке (asyncpg), не supabase-js.
- CI: джоба e2e в `ci.yml` переезжает на `uv run pytest -m e2e`; кэш браузеров
  `~/.cache/ms-playwright` сохраняется. Фронт остаётся на Bun.
- Удаляются: `frontend/e2e/`, TS-конфиг e2e, скрипт `test:e2e` в package.json.

## Реальные TG-тесты

Два слоя, оба под маркером `real_tg` (запуск: `uv run pytest -m real_tg`),
в отдельных каталогах, чтобы CI гонял их раздельными джобами:

1. **Бэкенд-слой** (`tests/real_tg/backend/`): настоящий app (`create_app` с
   боевой конфигурацией, без фейков) + фикстура-проверяющий. Сценарии:
   - проверяющий пишет мимику → агент отвечает через настоящий Telethon →
     ответ реально возвращается проверяющему; в Dev-базе появились
     `agent_messages` (входящее и исходящее) и события активити;
   - `POST /api/v1/agents/{id}/messages/trigger` → сообщение уходит в реальный
     Telegram и доходит до проверяющего.
2. **Фронт-слой** (`tests/real_tg/frontend/`, pytest-playwright): поднимается
   **настоящий** бэкенд (не тестовый сервер) и фронт. Бэкенд стартует с
   `RESTORE_RUNNING_AGENTS=false`: иначе lifespan поднял бы все RUNNING-агенты
   Dev, включая реальных агентов разработчика, и параллельное подключение
   убило бы их Telegram-сессии (`AuthKeyDuplicatedError`). Сценарий:
   - *диалог*: логин под реальным сайт-аккаунтом → страница агента →
     проверяющий импортируется напрямую (CLI-режим не нужен) → пишет мимику →
     в дашборде видны входящее и ответ агента, ответ подтверждается
     проверяющим.

Онбординг мимиков тестами не покрывается: это разовая ручная операция через
дашборд (визард с настоящим номером, код из SMS вводит человек). Тесты
работают только с уже заведёнными агентами.

Фронт-слой не несёт маркера `e2e`: `-m e2e` не должен собирать тесты,
ожидающие настоящий бэкенд. Выбор сервера фикстурой идёт по маркеру теста.

Настройка перед первым прогоном: регистрация сайт-аккаунта → ручной онборд двух
мимиков через дашборд (модель — с бесплатным вариантом каталога: Ling 3.0
Flash VL или Laguna S 2.1) → session string проверяющего скриптом входа.
Фикстуры проверяют выбор модели и падают с подсказкой, чтобы прогоны не жгли
платные токены. После этого регулярные прогоны полностью автоматические.

## CI

- `ci.yml`: e2e-джоба на Python, как описано выше. Реальных TG-вызовов в
  обычном CI нет.
- Новый `real-tg.yml`: только `workflow_dispatch` (ручной запуск). Джобы:
  бэкенд-слой (`uv run pytest tests/real_tg/backend -m real_tg`) и фронт-слой
  (`uv run pytest tests/real_tg/frontend -m real_tg`). Секреты:
  `TG_CHECKER_API_ID/HASH/SESSION`, `TEST_ACCOUNT_EMAIL/PASSWORD` +
  существующие креды Dev-базы.

## Безопасность аккаунтов и лимиты

- Одно сообщение на мимика за прогон, никаких петель с ретраями отправки.
- CI никогда не запрашивает коды входа: сессии уже сохранены, вход по коду —
  только ручной локальный сценарий.
- Проверяющий переиспользует одну сессию, никаких новых сессий на прогон.
- Креды только в `.env.test` (gitignore) и секретах GitHub; в репозиторий не
  попадают ни номера, ни session strings.

## Чистка файловых сессий

- `build_telegram_client` (`src/mimic42/integrations/telethon_client.py`):
  файловая ветка удаляется; клиент строится только на `StringSession`. Если
  `telegram_session_string` пуст — бросается `TelegramAuthorizationRequired`
  («сессия не сохранена — завершите онборд») до создания клиента и сетевых
  вызовов. Существующий маппинг API уже превращает эту ошибку в 428.
- `AgentRuntimeConfig`: поле `telegram_session_name` удаляется (рудимент
  файловых сессий); `telegram_session_string` остаётся опциональным — агенты
  без сессии существуют легитимно (черновики, UI-состояния), их конфиг
  строится, но старт громко падает на построении клиента.
- `POST /api/v1/agents`: поле запроса `telegram_session_name` заменяется на
  `telegram_session_string`. Фронт эндпоинт не использует (создание агентов —
  через визард онборда); тесты api обновляются.
- Колонка `telegram_sessions.session_name` в БД остаётся (историческая
  информация), миграции не нужны.
- Удаляются файлы: 21 файл `*.session` из корня, папка `sessions/`
  (2 файла), `PLAN.md`. Всё это вне гита (`.gitignore` покрывает), репозиторий
  не меняется. `.dockerignore` уже исключает `*.session` и `sessions/`.

## План тестирования

Сначала тесты на новое поведение, потом реализация (TDD):

- `build_telegram_client` без session string бросает
  `TelegramAuthorizationRequired` и не создаёт файлов;
- `POST /api/v1/agents` принимает `telegram_session_string`, без неё —
  422/428, никаких `.session`-файлов нигде;
- обновляются все тесты, передающие `telegram_session_name`;
- прогон существующих наборов: `uv run pytest -m "not db"`, `-m db`,
  `-m e2e` (переведённый набор зелёный до перехода CI);
- реальные TG-тесты гоняются локально после настройки (см. выше), затем
  руками дёргается `real-tg.yml`.

## Вне скоупа

- Автоматический приём SMS, покупка/хранение данных мимиков в секретах.
- Миграция прода и изменений в deploy.yml.
- Использование `session_name`-колонки БД где-либо кроме исторической.
