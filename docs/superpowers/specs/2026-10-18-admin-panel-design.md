# Админ-панель — дизайн

Issue: https://github.com/42-Z/Mimic42/issues/127

## Согласованный объём

В текущем сайте появляется раздел «Администрирование» в существующем тёмном
оформлении. Четыре подраздела: пользователи, пресеты, Telegram и статистика.
Отдельное приложение и отдельная авторизация не нужны.

Администраторов назначают и снимают вручную в базе. Через панель управляют
официальными и опубликованными пользовательскими пресетами, но не приватными.
Смена общей пары Telegram API ID/HASH действует только на новые подключения.
Изменения настроек и пресетов сохраняются в журнале без секретов.

Рабочая ветка — `feat/admin-panel` в текущей папке, без worktree.

## Доступ и границы подсистемы

- `public.admin_users`: `user_id uuid` — первичный ключ со ссылкой на
  `profiles.id`, `created_at timestamptz`. Наличие строки даёт административный
  доступ. Самоназначения, управления ролями через API и автоматического
  назначения первого зарегистрированного пользователя нет.
- У таблицы включён RLS; права `anon` и `authenticated` явно отозваны. Даже
  администратор не получает прямого клиентского доступа к ней.
- Источник полномочий — таблица, а не редактируемый профиль, `user_metadata`
  или устаревающий JWT-клейм. FastAPI сначала проверяет существующий Supabase
  JWT, затем читает назначение по `CurrentUser.user_id` на каждом запросе.
  После удаления назначения следующий административный запрос запрещён.
- `GET /api/v1/me` доступен любому вошедшему пользователю и возвращает только
  его UUID и `is_admin`. Он нужен для навигации, но не заменяет серверную
  проверку административных операций.
- Административные маршруты находятся под `/api/v1/admin` в отдельном
  `src/mimic42/api/admin.py` с общей зависимостью проверки администратора.
  Бизнес-правила и контракты отделены в `core/admin.py`, SQL-запросы и
  транзакции — в `integrations/database_admin.py`.
- Подсистема использует существующие асинхронные SQLAlchemy-сессии и
  серверное соединение с базой. В `api/app.py` остаётся её подключение к
  жизненному циклу приложения; перенос остальных маршрутов не требуется.
- Без JWT ответ `401`, без назначения — `403`, при недоступности хранилища
  — `503`, без разрешения доступа по умолчанию. Недоступность проверки роли
  не должна ломать обычные пользовательские разделы.
- Все ответы имеют явные модели публичных полей. Панель не получает
  содержимое переписок, память, промпты чужих агентов, Telegram-сессии,
  коды входа или сохранённые API HASH.

## Пользователи

`GET /api/v1/admin/users` возвращает постраничный список профилей приложения:
UUID, email из профиля, отображаемое имя, дату создания и количество мимиков
по состояниям. Поиск — по имени и email, размер страницы ограничен сервером,
порядок стабилен по дате создания и UUID. Пользователи без мимиков включены.

`GET /api/v1/admin/users/{user_id}` возвращает профиль и постраничный список
его мимиков: UUID, имя, модель и состояние. Обычный маршрут управления
агентом не становится доступен администратору другого владельца.

Состояние учитывает текущий менеджер рантаймов по тому же правилу, что
существующий список агентов: сохранённое активное состояние без загруженного
рантайма не выдаётся за работающий процесс. Подсчёты выполняются группами,
без отдельного SQL-запроса для каждого пользователя.

Удаления, блокировки пользователей, изменения их профилей и управления
чужими агентами в этом разделе нет.

## Пресеты и модерация

Административный список включает официальные пресеты (`owner_id is null`)
и пользовательские с `published_at is not null`, в том числе скрытые.
Приватный пресет не возвращается ни списком, ни по известному UUID: ответ
`404`. Ограничение проверяется при чтении и непосредственно при изменении,
чтобы одновременно снятый автором пресет не подвергался модерации.

Для официальных доступны создание, редактирование названия, описания,
промпта и настроек инструментов, порядок показа и включение/скрытие.
Существующий редактор пресетов переиспользуется. Владелец и slug не
переназначаются; новый официальный slug генерируется сервером. Операции
выполняются сервером, не расширяя клиентские права записи официальных строк.

Для опубликованных пользовательских доступны просмотр и скрытие/возврат
в каталог. Администратор не редактирует текст от имени автора и не меняет
владельца. `is_active = false` служит признаком административного скрытия;
автор не может изменить его через клиентский API. Снятие и повторная
публикация не сбрасывают этот признак.

При скрытии:

- пресет исчезает из магазина и доступного чужим пользователям выбора;
- существующее живое избранное замораживается по текущим правилам проекта;
- уже применённые настройки мимиков и замороженные копии не меняются;
- автор по-прежнему видит свой пресет с отметкой «Скрыт администратором»
  и может редактировать, снимать с публикации и удалять его;
- снятый с публикации пресет становится приватным и перестаёт быть доступен
  через административный API. Повторная публикация скрытого пресета не
  открывает его магазину, но снова делает доступным для модерации.

RLS чтения каталога и добавления в избранное, представление авторов и
триггеры учитывают активность опубликованного пресета. Клиентское чтение
не отфильтровывает скрытые собственные строки. Новые обходные разрешения
для `authenticated` не добавляются.

Заморозка при скрытии и запись аудита входят в ту же транзакцию. Возврат
пресета не оживляет замороженные копии. Физическое удаление официальных или
чужих пользовательских пресетов через админку не требуется.

Маршруты: `GET/POST /api/v1/admin/presets`,
`GET /api/v1/admin/presets/{preset_id}` для просмотра,
`PATCH /api/v1/admin/presets/{preset_id}` для официальных и отдельный
`PATCH /api/v1/admin/presets/{preset_id}/visibility` для видимости.
Изменение одной строки по UUID не затрагивает другие пресеты.

После мутаций обновляются административные и пользовательские кеши пресетов
текущей вкладки. Вместо бесконечной свежести каталога вводится периодическое
обновление не реже раза в минуту в активной вкладке и при возвращении к ней.
На уровне базы ограничение вступает в силу сразу.

## Общие Telegram API ID/HASH

`public.platform_telegram_settings` хранит одну строку с фиксированным ключом:
API ID, зашифрованный API HASH, время обновления и UUID администратора.
RLS включён, клиентские права явно отозваны. Шифрование — существующий
`FernetSecretCipher` с `SECRET_KEY`, как у Telegram-сессий.

`GET /api/v1/admin/telegram-settings` возвращает эффективный API ID,
признак наличия HASH, источник (`database`, `environment`, `unconfigured`)
и метаданные обновления. HASH и ciphertext не возвращаются. Поле HASH
в форме всегда пустое; сохранение требует ввода полной новой пары.

`PUT /api/v1/admin/telegram-settings` валидирует и атомарно сохраняет оба
значения вместе с аудитом. Без ключа шифрования сохранение запрещено.
Ошибки валидации и журналирование не должны повторять переданный HASH.
Форматная проверка не выдаётся за подтверждение работоспособности пары
Telegram: отправка кода не выполняется ради проверки формы.

Общий серверный поставщик настроек читает сохранённую пару при начале
нового подключения. Если строки ещё нет, используется существующая пара
`TELEGRAM_API_ID/HASH` из окружения. Сбой чтения базы или расшифровки не
маскируется возвратом к старой паре. После сохранения перезапуск не нужен.

Оба существующих пути создания агента используют тот же источник defaults,
не меняя контракт явно передаваемых учётных данных. Уже начатая авторизация,
перепривязка и работающий мимик продолжают использовать пару, сохранённую
в своей сессии. Массовой замены данных сессий и перезапуска агентов нет.

## Статистика

`GET /api/v1/admin/statistics?days=7|30` агрегирует данные всех мимиков на
сервере, не выгружая сырые сообщения и события в браузер.

- Пользователи: количество текущих профилей.
- Мимики: количество текущих агентов и распределение по эффективным
  состояниям рантайма.
- Сообщения за период: записи `incoming` и `agent_response`, как в текущей
  аналитике. Это записи диалога, а не гарантия доставки каждого ответа.
- Действия за период: события `tool.%`, включая неуспешные вызовы.
- Ошибки за период: события со статусом `failed`, не уникальные инциденты.
- Входные и выходные токены: сумма `agent_token_usage` текущих агентов за
  всё время учёта, независимо от выбранного периода. Дневной истории и
  подтверждённой стоимости в существующей схеме нет, они не изобретаются.

Графики показывают сообщения, действия и ошибки по дням. Диапазон включает
текущий день и предыдущие 6/29 дней; границы и группировка единообразны в
UTC, часовой пояс указан рядом с периодом. Пустые дни заполнены нулями.
Независимые агрегаты не перемножают строки при соединениях.

История удалённых агентов уже удаляется каскадно; статистика явно относится
к сохранившимся данным, а не к неизменяемому биллинговому журналу.
Индексы для глобальных временных выборок добавляются в миграции по
реальным предикатам запросов. Ошибки загрузки не отображаются как нули.

## Журнал изменений

`public.admin_audit_log`: UUID записи, UUID действовавшего администратора,
действие, тип и UUID изменённого объекта, ограниченные JSON-метаданные и
время. Для общей настройки объект определяется типом без UUID.
Клиентские права отозваны, RLS включён.

Журнал содержит, например, изменение видимости, порядка или признак
замены Telegram-пары. HASH, ciphertext, тела промптов и полные запросы
не записываются. Аудит и изменение фиксируются одной транзакцией:
при ошибке аудита изменение не сохраняется. Интерфейс отдельного журнала
в объём этой задачи не входит.

## Интерфейс и состояния

`/admin` открывает статистику; `/admin/users`, `/admin/presets` и
`/admin/telegram` — остальные подразделы. Сохраняются текущие Sidebar,
Header, адаптивная оболочка, семантические токены и shadcn-компоненты.
Административная навигация отделена от управления собственными агентами.

Пункт меню появляется после подтверждения роли. Администратору без
собственного мимика доступен `/admin`, без принудительного онбординга.
Обычный пользователь при прямом переходе видит отказ в доступе; чужие
данные не загружаются до проверки. При отзыве роли административный кеш
очищается, защищённое содержимое скрывается.

Списки имеют поиск и пагинацию. Для каждого подраздела предусмотрены
загрузка, пустое состояние, ошибка с повтором и успешное сохранение.
Во время мутации повторное действие недоступно; при ошибке несекретные
введённые данные не теряются. В форме Telegram явно указано, что новая
пара применяется к новым подключениям. Мобильный экран не требует
горизонтальной прокрутки всей страницы.

## Проверка и выпуск

- Проверить отказ для гостя, обычного пользователя и администратора после
  удаления назначения; самоназначение через Data API недоступно.
- Проверить поиск, пагинацию, пользователей без агентов и состояния
  незагруженных рантаймов.
- Проверить официальные мутации, недоступность чужих черновиков по UUID,
  скрытие, заморозку избранного и невозможность обойти скрытие публикацией.
- Проверить атомарность и шифрование Telegram-пары, отсутствие секретов
  в ответах, сохранение данных старых сессий и новое подключение без
  перезапуска сервера.
- Проверить точные агрегаты на известных данных, пустые дни и границы UTC;
  токены не меняются от переключения периода.
- Проверить административные и обычные пользовательские экраны на
  компьютере и телефоне, включая отсутствие собственного агента.

Миграции создаются и применяются Supabase CLI сначала в тестовой базе.
Назначение конкретного аккаунта администратором выполняется отдельно
вручную в базе и не зашивается в миграцию. Продукционные настройки и
назначения в процессе разработки не меняются.

PR открывается только после локальной проверки и подтверждения пользователя.
Перед этим выполняется предусмотренный проектом полный набор проверок;
во время разработки — только проверки изменяемых сценариев.
